# 中位标定心跳超时修复

日期：2026-09-10

产品：`patrol_vehicle_chassis`

## 现场事实

2026-09-09 17:30 的最后一次标定会话已进入可调整阶段，但未产生点动或提交请求。最后一次按时送达设备的查询在 17:30:40；下一次查询 17:30:41 在平台入队，17:30:47 才发布到 MQTT。0.2.16 候选的可调整阶段租约为 4 秒，因此设备先进入 `phase=8, fault=1`，并把该静止心跳超时提升为全局运动执行故障。取消会话虽恢复 `phase=0`，但没有清除 `faultLatched`，后续平台入口被门禁禁用。

同期生产 worker 多次记录主数据库忙。它与六秒派发延迟相关，但现有日志不能唯一确认具体锁持有者。已证实的问题是标定心跳通过普通持久化操作队列派发，而固件四秒窗口小于现场观测到的队列延迟。

## 0.2.17 与平台 0.4.99 修复

- 固件把无运动请求的 `CENTER_CAL_READY` 查询租约增加为 15 秒。
- `CENTER_CAL_READY` 心跳超时仍保留失败阶段、撤销许可并关闭车辆电源输出，直到平台显式取消；由于此时转向执行器必为 `BENCH_IDLE`，不再生成 `BENCH_FAULT` 或锁存全局运动故障。
- 转向点动、停止、提交、编码器写入或反馈门禁阶段的超时和故障继续停机、下电并锁存，安全语义不变。
- 页面不再因为心跳任务正在等待而丢弃用户动作；用户点击后，页面先等待当前只读心跳完成，再向保持单操作串行的 API 发送点动或提交。
- 固件冻结每次标定会话的首个失败现场，包括精确原因、安全门禁位图、失败时两路原始值和轮速、样本年龄、CANopen 执行步骤/故障、状态字、编码器事务状态与最近 SDO Abort；命令拒绝也返回最近拒绝原因，不再只有笼统 409 文本。
- `get_can_diag` 增加编码器当前值、在线/配置状态、最近错误类别和分类型累计计数。平台收到 `phase=8` 后持久化失败快照和原操作时间线，并幂等排入一次只读 CAN/编码器诊断；页面直接显示原因、门禁、关键证据和建议检查项。平台不会自动重放任何写入或运动命令。

## 证据边界

本修复需要通过 Python/主机回归、Web 语法检查和 ARM Release 候选构建。上述结果只证明源码、主机逻辑和构建产物，不证明真实转向、编码器 2048 写入、机械中位或异常掉电恢复已经通过。正式现场复测仍需核对操作记录中出现 `jog_center_calibration`，观察两路原始反馈随每次点动一致变化，并在提交后取得连续三次 2048±2 的新读数。若失败，先保全 `chassis_center_calibration_failed` 审计、对应 `get_can_diag` 结果和设备 `CENTER_CAL` 日志，再按失败原因检查；不要先取消、重启或重复提交后才取证。
