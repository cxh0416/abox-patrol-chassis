# 巡防车底盘逐车标定与参数记录

内部当前运维说明，面向 `patrol_vehicle_chassis`。正式固件以发布清单及哈希为准；现场结果查阅对应日期记录，不把源码实现当作现场验收。闲置降频后的查询唤醒和流量策略见[遥测流量与诊断策略](遥测流量与诊断策略.md)。

## 参数与持久化边界

| 项目 | 当前候选要求 | 保存位置 |
|---|---|---|
| 独立编码器 | 4096 count 单圈，机械中位置零，单圈跨零计算 | 编码器中位写入及 ABox 配置记录，持久性须实测 |
| 驱动器中位 | 本车机械摆正时的 Node 1 `6064` | ABox 配置页逐车保存 |
| 驱动器/编码器比例 | 2710.8 / 55.25 count/轮胎度 | 产品公共基线，不逐车复制旧采样结果 |
| 方向与容差 | 右转为正，双角度偏差 ≤2° | 产品安全配置 |
| 当前目标范围 | ±30° | 反馈硬保护与驱动器 RAM 软限位为 ±30.5°；边界回退到 29.5° |
| 上电运行中位 | 静止时依据独立角度重新建立 | RAM，断电或失效后清除 |

运行软限位写入后必须复读，**不执行控制器 EEP 保存**。历史 `Z0±27778`、±50°机构轴范围和旧编码器中心仅保留为历史记录，不直接套用于当前候选。CAN 参数及控制器配置基线变更必须按厂商资料单独确认，不能混入中位标定流程。

## CAN 遥控器只读观察

本机观察工具为 `E:\1_work\ChassisCar_test\chassis_can_remote_monitor.py`，独立于运动脚本，只通过 CANalyst-II 的 `Mode=1` 只听模式接收，不发送 NMT、SDO、运动或参数写入。它不读取车辆档案，不需要指定 `--car`。默认 500 kbps，保留帧类型、ID、DLC、原始字节及适配器时间戳，同时显示两套有差异的遥控协议候选。具体参数及 JSONL 保存方式见工具同目录 README 第 9 节。

要核对“遥控器 → A-BOX CAN2 → A-BOX CAN1 → 电脑”，遥控 CAN 接收模块只接 CAN2，CANalyst 物理通道 1 接独立 CAN1 段，然后运行：

```powershell
python E:\1_work\ChassisCar_test\chassis_can_remote_monitor.py --channel 0 --label CAN1-forwarded --dll "E:\canalyst-II-Driver\CAN\二次开发库文件\x64(64bit)\ControlCAN.dll"
```

板上须实际运行开启网关的固件；本地 `OfflineRemote` 产物配置不能代替烧录确认。现有网关仅转发标准数据帧，扩展帧与远程帧不会出现在另一段。排除其他发送源、两段误短接后，CAN1 侧出现对应帧支持 A-BOX 接收转发成功，仍不证明固件业务解析或允许车辆运动。

若先直接观察 CAN2，将分析仪物理通道 2 并联在 CAN2，改为 `--channel 1 --label CAN2-parallel`；这只证明总线存在报文，不能当作 A-BOX 接收证据。只听分析仪不提供 ACK，需正常接收节点。不得同时运行原控制脚本或其他 CAN 工具占用适配器。`--demo` 为离线合成输出，不加载 DLL 或接触 CAN。

Excel 候选为摇杆 `0x11A`、开关 `0x11B`；参考程序却用摇杆 `0x10B`、开关 `0x10A`，按键位置也不同。先保留原始帧，再逐项核验轴方向、符号、范围与按键含义；Excel 的 X1 起始位31/32冲突尚未解决。分别核对两类帧的新鲜度，并测试关闭手柄、保留接收模块供电后的行为；CAN 持续来帧不代表无线仍连接。原始现场抓包按 EVIDENCE 规则归档，不能与纯主机演示或构建日志混淆。

## 联网标定与网页键盘

保留联网固件，通过设备运维平台控制页 `/#/products/patrol_vehicle_chassis/control?vid=<本车VID>` 完成中位标定。网页本身具有独立远控能力，但本次硬件验收以 CAN 分析仪接 CAN2 的电脑键盘链路为准，按下节操作；不同时使用两种控制会话。

### 无 4G 时的 CAN2 标定

`patrol-chassis-0.2.86` 起，本地 CAN2 提供与网页维护相同的标定状态机。操作工具位于 `can2_center_calibration/`；当前车辆使用 CANalyst-II 物理 CH1 接 A-BOX CAN2，500 kbps。该入口只经 MCU 仲裁，不直接通过 CAN1 写驱动器参数。

先只读查询：

```powershell
.\can2_center_calibration\run_center_calibration.ps1 status
```

确认车辆架空或具备急停、双节点与编码器在线、双反馈新鲜、无故障锁存/OTA/其他控制会话，并由现场人员确认当前转向轮在机械中位后执行：

```powershell
.\can2_center_calibration\run_center_calibration.ps1 current
```

脚本执行 `START → READY → COMMIT → COMPLETE → POWER_OFF`。`COMMIT` 仍由固件先取得三组静止反馈，清除旧标定，发送编码器置零并在连续三次零点附近读数后保存 Config V5 和复读。不得仅凭 `COMMIT` 的接受响应认定完成。若车轮不在中位，使用 `interactive` 模式按 `±0.2°/±1°/±5°` 点动后再提交。

活动标定每 3 秒需要一次匹配查询，脚本在等机阶段持续轮询；关闭脚本、CAN2 Bus-Off 或 OTA 开始会请求取消。成功后必须完整断电重启，再查询确认 `calibrated=true`、保存中位与本次捕获值一致、编码器读数在 `0/1/2/4094/4095` 范围内。

2026-10-24 本车通过该入口提交当前中位 `-8122`，编码器置零并读回 `0`，Config V5 读回 `calibrated=true`；MCU 复位后 `status` 仍读回保存中位 `-8122` 和编码器 `0`。首次完成时脚本把已失效令牌与 `phase=COMPLETE` 的组合误报为失败，设备实际已保存；工具现已把该终态识别为成功。完整整车断电后的编码器零点保持仍需验收，见[本次证据](evidence/2026-10-24-can2-center-calibration-success-2026-10-24-150307-285589/index.json)。

先按下文标定流程完成机械中位提交，确认设备终态 `DONE` 且回读 `calibrated=true`、`profileCompatible=true`；结束标定会话并下电，后续用电脑脚本 P 上电、E 接管，核验两路新鲜角度及停车状态。用户指定的键盘默认值为 500 rpm、30°；真实验证需保持架空和急停，分别记录转向、回中、行走、松键、换向与断链结果。CAN2 指令经 MCU 仲裁，不直接透传 CANopen。

从 `0.2.62` 起，正常、已标定、运行坐标有效且安全条件满足的转向初始化可识别 `201A=2019=0` 空限位，随后经 ±30.5° RAM 写入并复读，成功后才继续使能；不写 EEP。标定点动仍服从当前驱动器限位，空限位不能通过点动扩展。现场已人工确认机械中位时，可在 READY 直接提交；未确认机械中位时不能以此绕过摆正过程。其他倒置/非零等值限位、缓存后变零及复读不一致保持故障。

2026-10-20 第二台车提交后设备只读结果为 `calibrated=true`、驱动器中位 `-1464`、独立编码器中位 `0`，见[标定后读回](evidence/2026-10-20-car2-after-center-093417/index.json)。车上现已安装 0.2.63，App 与启动状态逐字节校验通过，Boot 与配置未改，见[安装证据](evidence/2026-10-20-car2-install-0263-102312/installation.index.json)。真实转向和键盘运动仍待验证；首次零目标初始化出现 HallErr；检查反馈插头后消失，5 秒零目标及完整停机下电复查已通过，实际动作仍待现场确认，当前状态以 CURRENT 为准。电脑档案及固件逐车表的旧 `-1463` 为此前登记值，不能作为本次新 Flash 中位；逐车匹配构建前先同步核验，当前正式包 `PATROL_ACTIVE_CAR=0` 使用本车 Flash 标定。上电运行中位由静止双反馈建立，与 Flash 标定中位是不同字段。平台认证操作详情未读取，设备读回不能替代审计操作 ID/状态。

安装前若用 SWD 只读核验，先确认车辆输出已关闭、无接管/使能、标定执行器空闲且 OTA 空闲，保存 App、Boot State 和受保护的 Config V5 备份。J-Link 默认连接失败会尝试复位连接；只读检查应在 `connect` 前设置 `exec InhibitConnectRetries = 1` 及 `exec ForceAttachTarget = 1`，失败即退出，不自动改为复位连接或擦除。选项语义见 [SEGGER Command Strings](https://kb.segger.com/J-Link_Command_Strings#InhibitConnectRetries)。检查 VTref、SWD 接线并确认现场停机条件后才恢复连接；探针电压正常不能证明 SWD 通信正常。正式包安装必须同时核对 App 与启动状态的版本、大小和 CRC，按本机实际文件布局操作，不将 Full 写入当作 App 更新，也不覆盖本车配置。

## CAN2 电脑键盘硬件测试

当前使用 `E:\1_work\ChassisCar_test\chassis_offline_remote.py`，CANalyst-II 物理通道 2 接 A-BOX CAN2，500 kbps，A-BOX CAN1 接转向与行走驱动器。网页维护标定，电脑键盘通过 MCU 的本地 CAN 指令服务控制；不依赖网页接管、不直接透传驱动器 SDO。字节协议见[本地 CAN 控制协议](../protocols/巡防车底盘本地CAN控制协议.md)。0.2.63 已安装并获得真实 CAN2 三帧状态响应；首次 HallErr 经断电检查反馈插头后消失，后续 5 秒零目标测试通过。正常停机先空格撤管，等待至少 2 秒让执行器完成停机，再 O 下电；立即切断动力可触发保护锁存，不以此认定 HallErr 复发。实际 A/D 转向和 W/S 行走仍须现场核验。

只读检查：

```powershell
python E:\1_work\ChassisCar_test\chassis_offline_remote.py --can2-status --channel 1 --dll "E:\canalyst-II-Driver\CAN\二次开发库文件\x64(64bit)\ControlCAN.dll"
```

该命令只 QUERY，不上电、不接管，也不在退出时改变车辆输出。输出关闭时节点离线或反馈过期不代表通信失败；能得到匹配序号的三帧响应才证明本地 CAN 控制链路有回应。

反馈故障排除后，架空并备妥硬件急停，在独立控制终端运行：

```powershell
python E:\1_work\ChassisCar_test\chassis_offline_remote.py --car 2 --channel 1 --speed 500 --angle 30 --dll "E:\canalyst-II-Driver\CAN\二次开发库文件\x64(64bit)\ControlCAN.dll"
```

按用户要求，默认值也是 500 rpm、30°。P 仅上电，等双节点/双转角反馈新鲜且就绪后，在方向键全部松开时按 E 接管；先分别验证 A/D 原地转向与松开回中，再验证 W/S 及组合按键。记录现场实际车轮动作、双转角与轮速，不能只凭目标、ACK 或构建结果判定成功。空格停机并撤管，O 下电，R 在下电后请求复位运动故障，Esc/Ctrl+C 分别尝试 STOP/OFF 后退出。失焦撤管，重新聚焦须松开 E 后再按 E；MCU 租约 300 ms，QUERY 不续租。任一反馈拒绝、驱动故障或断链均不自动恢复控制。

`--car 1..4` 是操作者选择，不能识别实车身份。电脑 `car_profiles.json` 只作逐车档案/缺项门禁；正常 CAN2 目标模式的标定和运行坐标以 MCU Flash Config V5 及实时双反馈为准。CAR3/CAR4 未登记时拒绝正常控制。`--show-car-profile` 可离线查看档案，不加载 DLL；`--dry-run` 只测试编码器/响应组合，不能代替现场验收。

旧 SDO 类与 `--diagnose-steering`、`--restore-steering-limits` 仅保留为独立参数维护代码，不属于当前正常控制链路，不能通过本地目标协议直接访问驱动器对象。旧透明网关排查过程见[历史记录](history/2026-10-20-can2-gateway-debug.md)，不得重新启用绕过 MCU 仲裁的运动网关。当前转向初始化针对已知 0/0 空限位的 RAM 恢复仍需运行坐标和双反馈门禁，写后复读，不保存 EEP。


2026-10-22 操作者更换 CAR2 的 A-BOX 和车轮后，现场确认当前机械中位；本次三次独立驱动器读取均为 **-83815**，编码器置零前为 3963，置零后三次新样本为 0。仅对该板 Config V5 保存中位 **-83815 / 0**，重启主控后 `calibrated=true`、`encoder_profile_ready=true` 已读回，Boot/App/State/恢复页保持原样。[本次离线维护证据](evidence/2026-10-22-car2-center-maintenance-135252-400118/index.json)。本次实测值适用于该次更换后的硬件，不覆盖上述旧板历史记录；源码表的旧值在 `PATROL_ACTIVE_CAR=0` 构建中不用于加载中位，无需为此修改公共固件。仅核验主控重启后的配置加载与静止反馈，尚未验证整车完全断电保持或真实运动。此次受限 SWD 离线维护不作为下列正常平台标定流程的替代操作步骤；其 RAM 地址不得跨固件复用。

## 当前标定步骤

1. 核对 VID、固件版本、安全配置、驱动器与编码器型号，备份两节点当前参数；为每台车创建独立记录。
2. 保持架空与可用的本地安全停止条件，结束普通远控会话；确认 OTA 空闲、节点和反馈在线、无 Bus-Off/驱动故障、行走未使能、车辆电源输出命令开启，并取得左右静止反馈。本车没有独立的接触器反馈输入。
3. 开始独占 `start_center_calibration` 会话。新车、跨圈或旧标定不满足条件时，以会话起点两路原始值建立临时相对坐标，不套用旧绝对角度。
4. 使用 ±0.2°/±1°/±5° 逐步点动到现场确认的机械中位；若现场已确认机械中位，可不点动直接提交。每次点动均保留并服从驱动器当前软限位，两路相对变化差值不得超过 2°；相对会话起点另有 ±60° 兜底边界。`READY` 自进入起有 10 分钟纯空闲期限，查询不续期；空闲过期显示 `EXPIRED`，不生成设备故障。页面在点动或提交前等当前查询结束，以保持操作串行；查询失败只提示，实际请求由设备裁决。失联、离开页面或故障时取消并核验停机。
5. 人工确认车轮机械摆正后提交 `commit_center_calibration`。设备先停机并取得三组静止反馈，捕获驱动器计数，清除旧标定并回读，然后发送置零命令 06/0003/000F，连续三次新读数处于零点±2 count（0、1、2、4094、4095） 后保存逐车中位并回读。
6. 轮询 `get_center_calibration` 的 `IDLE/READY/BUSY/DONE/ERROR` 与 `reason`，至完成或失败，并复读配置。提交清除旧标定后失败保持未标定，输出禁用；不能凭 ACK 判定成功，也不能重放不确定的编码器写入。诊断明细按需通过 `get_center_calibration_diagnostics` 查询。
7. 成功结束撤销会话、清空 RAM 运行坐标并关闭电源输出命令。重新上电后核验配置、单圈范围、两路角度和静止坐标，确认没有自动接管。
8. 依次完成小角度、0°/±20°/±30°、范围异常拒绝和意外掉电恢复验证，将实际结果写入本车记录。停止、换向、断链及故障门禁持续有效。

在线 `set_calibration`、`clear_calibration` 已移除；目标接口见[巡防车底盘内部运维协议 V2.3](../protocols/A-BOX巡防车底盘内部运维协议-V2.3.md)，既有事务证据见[历史实现记录](history/2026-09-14-028-中位置零修复与验收.md)。
